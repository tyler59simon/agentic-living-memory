# Recovery and history

Every canonical/configuration mutation records preimages, postimages, hashes, and durable intent under STORE/.operations/OPERATION/journal.json before writes. A single OS store lock serializes cooperating writers. A crash can leave a partially applied operation; it is recoverable, not instantly atomic across the entire filesystem.

Run `doctor` to discover pending operations, `history` to inspect receipts, and `recover OPERATION --direction forward` to finish or `--direction backward` to restore. Backward applies only to unfinished operations: a `committed` operation is reversed through `undo OPERATION`, and a `rolled_back` one cannot be finished forward. Each write first rolls forward any pending operation and reports it as `recovered`; one it cannot finish appears in `warnings` with the `recover OPERATION` or `recover OPERATION --abandon` command to run. Recovery preflights every touched path against known pre/post hashes before the first write, preserves unknown user edits, validates journal content, and can resume after another interruption. Rebuild derived indexes/views after external repair; CLI recovery attempts reconciliation for affected domains. Canonical Markdown remains authoritative if derived regeneration fails.

The pending marker is written before the journal, so a crash between the two leaves a marker without a journal, and the next write removes it. `undo OPERATION` returns a note to its earlier text and location, and refuses when later edits would be lost. `restore REF` is different: it moves a note archived earlier forward to `notes/` and keeps edits made to other notes since, which `undo` of the archive cannot do. A completed operation can be reversed through `undo OPERATION`, followed by inspection and approved application of the resulting plan. It rejects later conflicting edits. Keep journals/backups private: they contain historical note and configuration preimages. Maintenance telemetry reset does not delete these recovery records. The only journals ever deleted automatically are committed Obsidian sync bookkeeping (`overlay_views`, `overlay_sync`, `overlay_state`) older than 14 days, at most once a day from session housekeeping.

Journals cover script operations, not the store folder itself. `backup` writes a verified zip of the canonical set (notes, archives, bindings, taxonomy, schema version; no indexes, journals or turn state) to STORE/backups and keeps the newest 7. Session housekeeping takes one at most daily (Claude SessionEnd, Codex SessionStart), and `doctor` and SessionStart warn when none is newer than 48 hours. A file that is not a readable note or configuration does not stop the snapshot: it is saved byte for byte and listed under `unreadable`. Rotation never deletes an older snapshot holding at least twice the notes of the new one (and at least 5 more); those are listed under `retained` with a warning, because a store that shrank that much may have lost a folder. Backups live inside the store, so copy `backups/` elsewhere or keep the store under git to survive losing the whole folder. `restore-plan FILE` turns a snapshot into an exact-hash plan for the domains it contains: review it with `inspect-plan`, then `apply`; it is journaled, so `undo` reverses it. Members outside the canonical set are rejected. Members that were unreadable when the snapshot was taken are skipped (`skipped_unreadable` in the plan summary): they are not restored, and the files now in their place are left alone.

Package install recovery is rooted at the install folder (`%LOCALAPPDATA%/agentic-living-memory` on Windows, `~/.local/lib/agentic-living-memory` elsewhere; the parent of `app/`). Harness wiring is rooted at each harness home, and legacy retirement at CODEX_HOME. Use `living_memory.py --root FOLDER history` and `recover` in the matching folder. The standalone installer lifecycle retains legacy receipts, durable package intents, and restartable rollback; rerunning its approved Python API plan resumes an interrupted operation. Receipt paths and hashes must remain intact.

Do not edit ownership records to suppress conflicts. Save and review modified files, then create a new plan. Corrupt JSON is preserved and reported rather than replaced. Recovering an older version may also require its compatible store schema; this migration intentionally preserves canonical note bytes.

**Automatic note maintenance.** A run reserves notes and money in `maintenance/runs/` before the model starts. If the worker dies, the next worker (or `maintenance run`) holds `maintenance/worker.lock`, settles every reserved, running or applying record as `interrupted`, frees an unused reservation and charges a launched run its whole reservation, so a crash never creates a new allowance. A note change that committed before the crash is not applied twice: each decision has a deterministic operation id. `maintenance status` lists unreadable run records under `errors` and reports `accounting_unavailable` when the allowance cannot be established; automatic runs then stop until the records are repaired. `.cache` holds only the temporary packet, and deleting it changes nothing. `backup` saves `maintenance.json`, `maintenance/state.json` and the run records. `restore-plan` keeps the current configuration but disabled (the snapshot's when the store has none), merges the checkpoint by element-wise maximum (counters, later `last_attempt_at`, any block and retry hold kept), and only adds run records: a current record is never deleted, and a final record replaces an unfinished copy but never the reverse. A restore therefore never lowers today's consumed allowance and never starts paid work; run `maintenance enable` again to resume. A relocation is refused while a run is unfinished or the worker lock is held (wait, or check `maintenance status`), does not copy `worker.lock`, and writes the destination's `maintenance.json` disabled. The retired source store refuses writes, so a worker that was still running there cannot change either store. `restore REF` undoes an archive, and `undo OPERATION` reverses any single maintenance change.
