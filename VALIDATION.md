# Validation

Run `py -3.15 -m unittest discover -s tests -v` from the project. Tests use temporary stores and installation targets and do not read your configured store; they do not fabricate production memories. The suite covers capture/deduplication, canonical staging isolation, retrieval ranking, strict SQL, corrupt config preservation, revision checks, taxonomy/secret rejection, governed undo, recovery after an actual process exit, simultaneous script writers, installer rollback/restart, install/uninstall preservation, native payload translation, capture completion, reference remap/undo, staged Obsidian promotion, generated canvas refresh, merge/lifecycle transitions, non-destructive migration, BOM/CRLF/YAML parsing, interrupted-transaction roll-forward and abandon, direct update/supersede and review dates, vault conflicts/renames/resets/properties, Stop-hook change detection, prompt relevance and dedupe, shell-safe command detection, conversational durable-statement reminders and their Claude delivery, the budgeted session-start index, short refs and exact-title lookup, vendor credential screening, and snapshot backup, retention, staleness and restore-plan round trips including rejected archive members.

`py -3.15 scripts/benchmark.py` constructs 100 synthetic notes and records 40 in-process search timings plus four conversational retrieval checks in .cache/benchmark.json. This small benchmark does not certify real-world recall. The <15 ms target is not a guarantee; measured full canonical freshness checks on this machine exceed it. Interpreter startup and native host overhead are additional.

`py -3.15 scripts/benchmark.py [--model-dir DIR]` also times, in process as a new hook would run them (p50 and p95, 15-20 runs): SessionStart in a bound git repo with a stale codebase map and brief, first session (no currency cache) against later sessions at the same HEAD (target second-session p50 under 250 ms); a prompt hook and a 10-question quiz prompt on 200 generated notes; and, with `--model-dir` (a verified potion model folder such as `<store>/.models/potion-retrieval-32M`, copied into the temporary store and skipped when absent), the same prompts with semantic search (target p50 under 120 ms) and the model load with and without `tokenizer.marshal`. Measured on this machine: session start 234-261 ms first, 49-55 ms second (254 ms before the currency cache); semantic prompt p50 97-108 ms, quiz prompt 103-115 ms (171 and 123 ms before the tokenizer cache, the lazy recent-note snippets and a faster cosine); model load 30 ms uncached, 11 ms cached.

`py -3.15 scripts/benchmark.py --scale 1000 [--semantic-from STORE]` builds a synthetic store of that many notes and times a prompt hook, a capture and a session start as a new process runs them (median of 7; `prompt_warm_ms` is what a long-lived `serve` process sees). `--semantic-from` copies an installed model from a real store so writes pay for embeddings as they do in use. It exits non-zero when the prompt hook exceeds 400 ms or the capture 1,500 ms. Measured on this machine at 1,000 notes with potion-retrieval-32M: prompt 276 ms, capture 464 ms, session start 334 ms (before the per-process scan memo and vector reuse: 760 ms, 3,795 ms and 3,545 ms).

`py -3.15 scripts/eval_retrieval.py --fixture FILE [--root STORE] [--json]` scores the real prompt-injection, session-start and durable-signal code against a fixture of prompts with the notes each should (`expect`) and should not (`forbid`) surface, and prompts labelled with the signal kind they carry. It reports hit@3, false-injection rate, forbidden injections, injected characters, session-start size and index coverage, and per-kind signal precision, recall and false-arm rate, listing every miss. A fixture's `quiz_prompts` (one question per line; a positive injects at least `min` of its `expect` notes, a negative none) and `interim` cases (`marked`: whether the injected line carries `UNCONFIRMED (as of ...)`) are scored too. A fixture with a `notes` list is synthetic and built into a temporary store (`tests/fixtures/eval_synthetic.json`, run by `tests/test_eval.py`). Otherwise it runs against your store without changing notes. Keep personal fixtures outside the repo, e.g. `~/LivingMemory/.eval/`. A ref that no longer resolves fails the run, so stale fixtures are visible. Change retrieval defaults only when this report improves. `--semantic on|off` sets whether the installed semantic model is used. It rebuilds the store's indexes to match, then rebuilds them again for the hooks; it is refused for synthetic fixtures, whose temporary store has no model. The report includes `mean_ms`, the in-process prompt retrieval time.

**Retrieval variants and section-level units (2026-11-12).** `py -3.15 scripts/eval_retrieval.py --fixture tests/fixtures/eval_units.json --config A|B|C|P|D|E [--model-dir <store>/.models/potion-retrieval-32M] [--json]` builds the synthetic fixture (12 notes, 60 seeded distractors, 32 single prompts, 4 sessions) in a temporary store, installs the model from `--model-dir` (hashes still checked) and scores one variant: A lexical, B the note-level Python vectors used before units, C the same vectors through sqlite-vec, P every section embedded and scored in Python, D the same through sqlite-vec, E D plus the injection controller. Each prompt is scored by rank (recall@1/3/5 and MRR over `search_domains`, no gate), by injection, by whether the injected text already holds the case's answer phrase, by polarity (a rejected option on a line without a rejection marker) and by characters (injected, plus one follow-up `read` when the note was injected without the answer: `read --section` under E, the whole body otherwise; tokens are characters / 4, an estimate). Sessions run the real prompt hook turn by turn. Measured on Windows 11, Intel i7-9750H, 16 GB, Python 3.15.2, SQLite 3.53.4, sqlite-vec 0.1.9: recall@1 1.0 in every variant (the fixture is too easy to separate them by rank); injected hit A 0.704, B and C 0.778, P, D and E 0.852; answer in the injected text B 0.444, D 0.481, E 0.778; false injection 0.0 in A to C and 0.2 (1 of 5 negatives) with units, where a short distractor section about "autumn" reached similarity 0.56 for a haiku prompt; polarity errors 0 everywhere; estimated tokens per answered prompt A 182, B 165, D 157, E 110; session steps correct 0.615 in A to D and 1.0 in E, with no repeated lines; in-process prompt p50 17 ms (A) to 20 ms (E). The older fixture (`eval_synthetic.json`) gives the same scores in every variant (hit@3 1.0, false injection 0.0, long prompts, quizzes and sources unchanged). Results and the baseline are in `docs/evaluations/sqlite-vec/`.

`py -3.15 scripts/benchmark.py --vectors N [--queries Q]` (SYNTHETIC random unit vectors, not a corpus) compares the Python scan and sqlite-vec's exact KNN over the same blobs: on the machine above, p50 per query 33 ms against 2.8 ms at 1,000 vectors, 334 against 25 ms at 10,000 and 3.4 s against 226 ms at 100,000, with identical top-20 lists on every query; the vec0 table adds about half again to the file size; loading the extension takes about 0.5 ms (1 to 1.7 ms the first time). `--hook-store STORE --hook-cwd DIR` times the real prompt hook as a fresh process against a store (use a copy: session state is written), native on and off: on a copy of an 87-note store (490 units), p50 399 ms native and 417 ms Python, against 389 to 401 ms for the code before units on the same kind of copy; process start dominates.

**Functionality simulation.** `py -3.15 scripts/simulate.py [--scenario NAME|all] [--harness claude|codex|copilot|factory|all] [--subprocess] [--package DIR] [--content] [--keep] [--out FILE] [--json]` runs scripted sessions through the real hook adapters and CLI. Scenarios live in `tests/scenarios/*.json`.

Each scenario runs once per harness it lists (default: all four) against a fresh sandbox store: a temporary folder marked with `sandbox.json`, selected through `LIVING_MEMORY_ROOT`, with every harness home pointed at an empty folder. Your store and configuration are never written.

Steps are sent in each harness's own wire format:
- Copilot gets camelCase names and JSON-string tool arguments; only Codex gets a `turn_id`.
- Claude and Factory send only `Write|Edit|MultiEdit|NotebookEdit|Bash|PowerShell|Read|Glob|Grep|Agent|Task` tool calls to the hook. Repeat Read, Glob and Grep calls are answered by `core/hookfast.py` without loading the runtime.
- Events a harness does not wire are skipped, not failed.

**Expectations** are checked against the adapter's parsed reply and the debug log's decision detail (see MAINTENANCE.md). Hook steps can expect `inject`, `inject_includes`, `path`, `gates`, `context_contains`, `context_excludes`, `deny` (a rule such as `protected:domains`, or `subagent`), `allow`, `reminder`, `stop_reason`, `mutation`, `hints`, `recall`, `private_notice`, `instructions`, `system_message`, `internal`, `level` and a `detail` subset. CLI steps can expect `exit`, `status`, `reason` and a `result` subset. `save`/`as` keep values and new notes for later steps.

**Invariants** checked after every step:
- one log line for the step that agrees with the reply;
- injected refs that appear in the delivered text and match the usage diary;
- no scenario `secrets` in the log, the diary or session state;
- no error line without an injected `fault`.

Each run ends with `validate` and `doctor`.

**Modes:**
- In-process (the default) is what `tests/test_simulation.py` runs. It also checks that a deliberately broken relevance gate is reported.
- `--subprocess` runs real processes.
- `--package` runs an installed copy, for example `--package %LOCALAPPDATA%/agentic-living-memory/app` after a deploy. Fault scenarios (`in_process_only`) are skipped there.
- `--content` also logs text (allowed only because the store is a sandbox) and checks that the logged context equals the delivered one.

The report goes to `.cache/simulation/<UTC time>.json`, and `--keep` keeps each store for inspection.

The simulation exercises Living Memory's side of each harness contract as written in the adapters. It does not prove what a live harness sends.

Native adapter fixtures establish wire-format behavior, not live support in every harness version. Claude Code and Codex are installed and used live on this machine; Factory and Copilot are checked against fixtures and vendor documentation only. Hook config alone does not prove trust or delivery: verify native `/hooks`, then check the last observed invocation in `doctor`. There is no fresh-machine or non-Windows installation test in this environment.

**Maintenance dry-run gate (MAINT-1F).** Before `maintenance enable` on a real store: (1) on a fixture or sandbox store, run `maintenance preview` (no model call, no allowance) and then `maintenance run --dry-run`, and check that every recommendation is sensible and no note changed; (2) on a copy of the real store (`--root` pointing at it), repeat the preview and one dry run against the real `claude` CLI, review the decisions with `maintenance history --run ID`, and confirm `status` shows the spend; (3) only then enable the real store, one domain at a time. A dry run spends the day's allowance and the 24-hour interval, so plan for that. The offline checks are `tests/test_maintenance*.py`, `tests/test_backup.py` (maintenance files and restore merge), `tests/test_storage.py` (relocation) and the Stale Notes dashboard test in `tests/test_review_worklist.py`.
