How I Fixed Memory Retrieval

Rebuilding Agentic Living Memory with SQLite-vec, hybrid search, and token-efficient context. The search was already finding the right notes. Most of what it handed the agent was the wrong part of them.

Fixture: 12 invented notes, 60 seeded distractors, 32 prompts and 4 sessions. Machine: Windows 11, Intel i7-9750H, 16 GB, Python 3.15.2, SQLite 3.53.4, sqlite-vec 0.1.9, model potion-retrieval-32M (512 dimensions). Nothing here was measured on agent task outcomes.

The problem

Living Memory keeps an agent's durable notes as Markdown files and injects the relevant ones into each prompt through native hooks. Before this work, its optional semantic search embedded each note's title and summary only, scanned every vector in Python, and fused that ranking with SQLite FTS5 by reciprocal rank. The prompt hook then injected one line per relevant note: the title and a 220-character window of the body.

That design found the right note most of the time. What it got wrong was what it delivered. Three things I measured or reproduced:

  • The answer was usually somewhere else in the note. Asked "what options did we turn down for token refresh?", the hook injected the note's summary and the opening of its reasons, then cut off before the rejected options. With note-level vectors, the answer was in the injected text for 0.444 of prompts.
  • Facts buried in sections were invisible to the vectors. A title-and-summary vector cannot know that a sync-service note says Osaka timestamps arrive in JST. Note-level vectors missed 6 of 8 paraphrased questions about buried facts.
  • Conversations broke it. "Why?" after a question has no searchable words, so it got nothing. Across four scripted sessions, 0.615 of steps were handled correctly.

Two things were design risks rather than measured failures: the Python scan grows linearly (synthetic: 3.4 s per query at 100,000 vectors), and the prompt hook had no total size budget, relying on Codex's 4,000-character limit to truncate from outside.

The constraints

Living Memory is a standard-library Python tool that runs inside hooks with a 15 to 30 second timeout and starts a new process for every prompt. The rules for this work:

  • No MCP server, no daemon, no database server, no embedding API, no extra model calls during a hook.
  • Canonical Markdown stays the only source of truth. Every SQLite file is derived and can be deleted.
  • FTS5 keyword search keeps working on a clean machine with nothing installed. sqlite-vec may speed things up but must never be required, because some Python builds cannot load SQLite extensions at all.
  • No network or downloads inside a hook; no note text in logs; Windows first (Python 3.15, file locking).

The user chose to ship sqlite-vec as an optional pinned pip package, and to keep Python cosine, FTS5 and the lexical gates working together as a complete fallback.

The insight

Nearest neighbours are candidate discovery, not delivery. Finding the note is one decision; deciding which part of it the agent needs, whether the session already has it, and whether it is worth the tokens is another. I kept the two separate: retrieval still answers "which notes are plausible", the existing relevance gate still answers "which are relevant", and a new controller answers "how much of each".

After

  1. Prompt → acknowledgment check → follow-up check (uses the previous prompt's note refs)
  2. FTS5 BM25 over notes (unchanged)
  3. Units: overview, caveat and every section embedded; best unit per note; sqlite-vec KNN or the same scan in Python
  4. RRF fusion, per-domain relevance gate (unchanged)
  5. Choose a unit: role cue, meaning, or shared words
  6. Dedupe by note revision, section and level
  7. Pointer, evidence (summary opening + section) or expanded, inside one 4,000-char budget

Inside the new engine

Memory units

core/units.py cuts each note into an overview (title plus summary, byte-for-byte the text the old note vector embedded), the > **Important:** caveat, and one unit per section heading. Headings inside fenced code are text. A section over 360 words splits between paragraphs, never inside a fence. Each unit gets a role from its heading: Why is rationale, Alternatives considered is alternative, Steps and Roll back are procedure. Unit ids come from the note id and the normalized heading path, so moving a section keeps its id; the text hash decides re-embedding, so moving a section costs no embedding and editing one re-embeds only that one.

The unit index and its backends

core/vectors.py keeps the units in a sidecar per domain, updated in one transaction per write that bumps a generation number. A reader sees the old generation or the new one, never a mix. The index stores the model identity, the vector dimension (read from the model file) and the note index's fingerprint; if any of them disagree, it is not read and search falls back to note-level vectors, saying so on every hit as backendReason.

When sqlite-vec loads, the same transaction writes a vec0 table and queries use its exact KNN. Retired notes are not stored in the vector table, so the query widens k until enough eligible notes appear. A note's score is its best unit, never a sum, so a long note earns nothing from its length. Without the extension, the identical embeddings are scored in Python with the identical tie-break.

The injection controller

core/injection.py picks one unit per relevant note. A role cue in the prompt ("why", "turned down", "fixed", "how do I") picks a section of that role. Otherwise a section wins over the overview when its similarity clears the model's 0.45 threshold and beats the overview, with 0.05 added per shared prompt word, or, without a model, when it shares at least two prompt words. The line then leads with the summary's opening, because a section's reasons only make sense next to the decision they support. A rejected-options section always carries a label saying so.

Reading it honestly

  • sqlite-vec changed speed, not results. B and C match exactly, as do P and D. On a copy of a real 87-note store (490 units), 24 of 24 queries gave identical top-20 lists, with the largest score difference 5.8e-7.
  • Section units bought a little recall and cost one false positive. They caught 2 of 8 buried paraphrases that note-level vectors missed. They also let "write a haiku about autumn leaves" match a short distractor section full of the word "autumn" at similarity 0.56. Short sections give peakier similarities. I kept the failing case in the fixture rather than tune a threshold around it.
  • The controller is where the gain is. Same retrieval as D, but the answer arrives in the injected text for 0.778 of prompts instead of 0.481, and follow-ups like "why?" and "what were the alternatives?" now work.
  • No regression on the older fixture. eval_synthetic.json scores identically in all six variants: hit@3 1.0, false injection 0.0, long prompts, quizzes and source excerpts unchanged.

The hard parts

sqlite-vec takes only its own ORDER BY distance

My first KNN query joined the vec0 result to the unit table inside a CTE. SQLite flattened it and pushed a second sort key into the virtual table, which sqlite-vec rejects. The fix was to run the KNN alone and resolve notes and tie-breaks in Python.

Importing the package loads numpy

import sqlite_vec imports numpy when it is installed, which costs a hook process real time. The loader finds the bundled vec0 library with importlib.util.find_spec and loads only that fixed path, with extension loading switched on for that one call.

Headings "Part 1" and "Part 2" were the same heading

My first heading normalizer kept letters only, so numbered sections got the same unit id, the unique constraint failed, and the whole unit-index update was rolled back. The failure was caught and logged by design, which is exactly why it was quiet. A test with eight numbered sections found it.

Windows would not replace a file I still had open

When the unit index was damaged, the reader returned "unreadable" but left its connection open. On Windows that handle blocked the rebuild's atomic replace. The reader now closes on every failure path.

Each new note was embedded twice

The note-level vector and the overview unit embed the same text. An existing test that counts embeddings caught the double work; the rebuild now hands its fresh embeddings to the unit index, and an edit that leaves the summary alone reuses the overview unit's vector.

Section evidence dropped the actual answer

For "when are the database backups taken", the best section was Details while the time was in the summary. Evidence lines now lead with the summary's opening. Separately, every section embedding includes the note title, so sections of one note score close together; a small bonus per shared prompt word separates them.

The Codex review found eight more

An independent review (Codex, gpt-6.1-sol, extra-high reasoning) of the whole branch found two P1 and six P2 issues. All eight were real. All are fixed, each with a regression test that I checked fails on the code before the fix and passes after.

  • P1 Follow-up topic notes skipped the learned-runbook publication check, so a suspended procedure could come back on "what are the steps?".
  • P1 read --section read the raw file instead of the approved body, exposing an unreviewed edit of a learned runbook.
  • P2 "why Redis?" after an outbox question was treated as a follow-up to the outbox.
  • P2 A question that found nothing kept the old topic, so a later "why?" answered the wrong thing.
  • P2 Post-compaction recall cut by the budget was still marked delivered.
  • P2 Fenced commands lost their newlines and indentation in evidence lines.
  • P2 Evidence lines dropped a learned runbook's usage-report hint.
  • P2 sqlite-vec could cut tied neighbours at k differently from the Python scan.

Lessons and tradeoffs

  • The cheapest gain was not in the index. Choosing which part of an already-found note to deliver beat every indexing change I measured.
  • A native backend is easy to make faster and hard to make different. Keeping native and Python on the same embeddings and the same tie-break made "identical results" testable, and the review still found a tie case.
  • Section vectors are peakier than note vectors. The 0.45 threshold was tuned on note vectors; it needs re-tuning on a harder fixture before I trust section-only matches more.
  • I deliberately did not add learned gates, bandits or usage-based suppression. The usage diary now records the delivery level and a surface event for candidates cut by the cap, so a future experiment has data, but "injected and not opened" is not treated as "unused".

How to use it

# optional native acceleration, into the Python the hooks run
py -3.15 -m pip install --user sqlite-vec==0.1.9
living_memory.py semantic rebuild        # rebuild units and the vec0 tables
living_memory.py semantic status         # backend, native: loadable/version, units per domain
living_memory.py search "why outbox" --explain
living_memory.py read REF --section "Alternatives considered"
living_memory.py semantic native off     # keep the extension unloaded; same results in Python

Without the package, nothing changes for the user except speed. To roll back entirely, check out an earlier release: its code ignores vectors.sqlite3, which can then be deleted. The deployed hooks run an installed copy, so none of this reaches them until install.py is re-run.
