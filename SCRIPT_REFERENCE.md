# Compact script reference

For `learn` (no arguments prints a guide), `learn record`, `learn ENTITY ACTION [ID]` with flags or JSON payloads, review plans (promote, rollback, retire, delete, prune) and `export --include-learning`, see [Reviewed learning](LEARNING.md). `version.capabilities.learning` advertises support independently of the stdio envelope API.

Use `python living_memory.py COMMAND --help` for exact arguments. Common options are `--root STORE`, `--domain DOMAIN`, `--cwd PROJECT`, and `--actor main|subagent|viewer`. Outputs are compact JSON. Stable references are `domain:id`; a REF may also be `domain:` plus a unique 8+ character ID prefix (the short form injected lines show), a bare ID or prefix in the active domain, or an active note's exact title (case-insensitive, active and parent domains; ambiguous matches fail with `ambiguous_ref`). IDs are unique across the store, so a `domain:id` whose note has since moved (promoted to the global domain, or remapped) still finds it in its new domain. Outputs and receipts always carry full IDs. Revisions hash the full note file.

Update payload: `{"body":"reviewed replacement","expected_revision":"FULL_FILE_SHA256"}`. Rename: `{"title":"New title"}`. Retag: `{"tags":["subject/project","concern/decision"]}`. Supersede: `{"superseded_by":"SUCCESSOR_ID"}`. Merge: `{"target":"domain:id","sources":["domain:other-id"],"body":"reviewed combined knowledge"}`. Payload-based commands read JSON stdin when `--payload-file` is absent.

Projects: a project is a `project/<slug>` tag plus an entry in `<store>/projects.json` (slug, name, status active|paused|archived, absolute `repos`, `aliases`, `description`, `charter` note ref). Projects exist only through `project-plan`, never `taxonomy-plan`. `project-plan create` payload: `{"slug":"hivemind","name":"Hivemind","repos":["C:/path/repo"],"aliases":["HM"],"description":"...","charter":{"domain":"optional","title":"optional","body":"The summary ..."}}` makes one plan (kind `project_create`) that adds the tag, the registry entry and the charter note (a `context` note tagged `project/<slug>`; domain: `charter.domain`, else the domain bound to `repos[0]`, else global). `update` takes `{slug, name?, repos?, aliases?, description?, status?, charter?}` (kind `project_update`) and `archive` takes `{slug}` (kind `project_archive`); both change only `projects.json`. `capture --project SLUG` adds `project/SLUG` to a new note; `update` has no `--project` because facet flags there replace the whole tag set (use `--tag`). `projects` and `doctor` warn about a missing repo folder, an unregistered project tag or a charter ref that no longer resolves. `projects.json` is protected config and part of `backup`.

Project auto-attribution: on capture only (never `update`, `supersede` or `retag`; batch and payload captures included), a note with no `project/*` tag gets one from the first level that matches an active project whose tag is in the taxonomy: (1) the note's own `files`, relative paths resolved against every prefix of the target domain; (2) with `--session`, the files this turn touched (the hooks' session state, stored the same way); (3) with `--session`, the cwd. Without `--session` the cwd is ignored, because `serve --stdio` passes the app's own cwd to every request. Per file the longest repo prefix wins, paths compare case-insensitively on Windows, and the union over the level's files is used: one or two projects are tagged and reported in `inferred_tags`; more than two add no tag and the result carries `project_candidates: [slugs]`. An explicit `--project` or `project/*` tag disables inference. A broken `projects.json` skips inference silently. SessionStart adds `Project: NAME (project/SLUG; capture with --project SLUG) — charter summary · charter REF` when the cwd lies in a project's repo (that project's open items sort first; the summary is the first thing dropped under budget pressure), or `Projects here: SLUG, SLUG — tag captures with --project SLUG` (160 characters at most) when the cwd lies above project repos.

Digest notes: any note may carry `sources: [{path, sha256}]` (at most 20; path text of at most 300 characters; sha256 64 hex digits), set by `capture --source PATH` and `update --source PATH` (repeatable; the file's current hash is computed; a path already listed takes the new hash). PATH is absolute, or relative to a folder bound to the domain (or to `--cwd`); the stored path is relative to the bound folder (`billing/README.md`, like `files`), or `name:rel/path` for a file of a registered source outside the bound folders; a file outside both is refused. With one `--source` and no `--idempotency-key`, capture uses the key `digest:<path>:<sha256>`: the same file content is digested once (a rerun answers `existing`, whatever the wording), and a digest of other content for exactly the same paths replaces the old one (`superseded`). Digests are exempt from the similar-title guard against each other, since each is about its own file. A note is a stale digest when a listed file's sha256 differs or the file is gone (a note in a domain with no bound folder is never called stale): prompt hits, file hints, SessionStart lines and `ask`/`search` results say `STALE: <path> changed since this digest` (`ask` also sets `stale` on the hit and prefixes its snippet), `review` lists stale digests (`stale_digests` count, `stale` on each row), and a `sources` path counts like a `files` entry for file hints and Stop follow-through when its file is edited. `update` with a body change and `confirm` record the files' current hashes (the author checked them); other updates do not. `sources` is system-managed: the Obsidian vault copy keeps it but cannot edit it, and the search index stores it in a `sources` column. `ingest-scan` ranks the knowledge-base index's files: decision records (`adr`; an ADR folder's README is a plain README), then READMEs and top-level docs, then wiki pages and other docs, then entry points and build files (`entry`, `build`), then modules ordered by how many other files' chunks mention their name and by size, then the rest (tiny modules `other`; tests `test`, which is anything under a `tests`, `spec`, `fixtures` or `testdata` folder, Markdown included, and which a search also ranks below code unless the query is about tests); `status` is `skipped` while the file's hash matches its skip marker (and no digest lists it), `current` when an active note's `sources` lists the path with the file's present hash, `stale` when it lists it with another one, else `new` (`digest` is that note's ref, `file` the path for `--file` when it lies in a bound folder, `abs` where to read it).

`scripts/ingest_run.py [--root R] [--domain D] [--cwd DIR] [--source NAME] [--batch 8] [--max-batches N] [--budget-usd X] [--parallel 1] [--all] [--model sonnet] [--command-json '[...]'] [--allowed-tools ...] [--timeout 1800] [--log FILE] [--dry-run]` drives headless agents over the `ingest-scan` list, one batch of files per agent run (the agent writes its digests through this CLI; LM itself calls no model). The agent argv template takes `{prompt}` and `{model}` (default `claude -p {prompt} --model MODEL --output-format json --permission-mode acceptEdits --allowedTools Read Glob Grep Bash(<this CLI>:*)`; without `{prompt}`, or for a Windows `.cmd` shim, the prompt goes to stdin; no shell). `--dry-run` prints the batches and prompts and runs nothing; by default only `new` and `stale` files are sent (`--all` adds `current` and `skipped` ones; `--changed-only` is an accepted no-op alias); `--budget-usd` stops starting batches once the agents' reported costs (`total_cost_usd` or `cost_usd`, their own claim) add up to it; `--parallel N` runs N batches at a time. Each agent ends with `{"digested": [paths], "skipped": [{"path", "reason"}], "failed": [{"path", "reason"}]}`; `failed` is a file whose capture was refused or errored, and it is never recorded as a skip. When Claude's JSON reports `permission_denials`, none of that batch's skips is recorded either (they are logged as failed, since a blocked capture may have been reported as a skip); a log row has `failed` and `permission_denials` (a count). The run log (JSON lines, one per batch plus a summary) goes to `<store>/logs/ingest-run-*.jsonl` or `--log`; stdout is the summary `{ok, batches_run, batches_planned, files_digested, files_skipped, files_failed, cost_usd, verified:{current, skipped, still_open}, batches_failed, log}`, where `verified` comes from a fresh `ingest-scan`, not the agents' word. A file an agent skips as trivial is recorded through `ingest-skip` (a main-agent write taking `{"skipped": [{"path", "reason"}], "clear": [path, ...]}`, either key or both, and answering `{ok, domain, recorded, cleared}`; `clear` removes the markers of those paths, so they read `new` again, and an unknown path counts 0) in the non-canonical sidecar `domains/D/.ingest-skips.json` (`{path: {sha256, reason, at}}`, newest 5,000; not validated or backed up) and shows as `skipped` in `ingest-scan` until its hash changes, when it is `new` again. Interactively, an agent works the same list a few files per turn.

Knowledge base: `ask` answers a question about the project (a chunk of a test file ranks a little below the code it exercises, unless the question mentions test, tests, testing or spec) from notes first, then from a deterministic library of source excerpts: the docs, wiki exports and code of the domain's sources, indexed in `domains/DOMAIN/sources.sqlite3` (FTS5, porter stems, camelCase words split; optional vectors when a semantic model is installed, embedding only changed chunks within a time cap). The index is derived: not canonical, not backed up, not in a relocation, rebuilt by `source-sync --rebuild`. A source is a folder (`kind` folder: docs and code), an HTML wiki export (`html-export`: headings kept, scripts, styles, nav, header, footer and breadcrumb or sidebar blocks dropped, table rows kept as lines) or a clone of a git wiki (`git-wiki`: Markdown, reStructuredText, AsciiDoc and HTML pages; a page without a heading is named by its file, `Retry-Policy.md` is "Retry Policy"). Every git repo under a bound folder (or the bound folder itself) is an implicit `folder` source named by its folder, with no setup (a linked git worktree of a repo already found is not a second source; the main checkout is kept). `source-plan add` registers another one in `<store>/sources.json` (`name` slug of 2 to 40 characters, since `w:Page.md` reads as a drive, `domain`, `kind`, absolute `path`, `include` and `exclude` globs, at most 20 each; an include glob indexes any matching text file) and `source-plan remove` drops it; `source-plan implicit` with `{"domain":"D","enabled":false}` turns the implicit repo sources off for a domain (`true` on again). Plans are main-agent writes the user approves, like `project-plan`; `ask`, `sources`, `search --sources`, `ingest-scan` and `source-sync` are auto-allowed and also allowed for subagents and viewers (`source-sync` writes only the derived index, as `search --rebuild` does for notes), except a sync that reaches the network (see Live wiki connectors below). The memory store itself is never indexed (`source-plan add` refuses a folder that is or lies inside it; one that merely holds it skips it), and a source holds at most 100,000 files (`truncated` in the sync result says so). Sync skips binaries (a NUL byte in the first 8 KB), files over 1 MB, symlinks, hidden folders (except `.github`), `.git`, `node_modules`, `target`, `build`, `dist`, `.venv`, `venv`, `__pycache__`, `.idea`, `.gradle`, `vendor`, `bin`, `obj` and the like, and whatever the top-level `.gitignore` names (the common patterns: `*`, `?`, `[..]`, `**`, `/anchored`, `dir/`, `!negation`). Credentials are replaced with `<redacted type='KIND'/>` (the detector `capture` uses) before anything is indexed, keeping line numbers. Files are cut into chunks of about 1,200 characters with a small overlap, at headings (Markdown, reStructuredText, AsciiDoc, HTML) or top-level definitions (Python, Java, Kotlin, C#, TypeScript and JavaScript, Go, Rust, COBOL divisions and paragraphs, SQL statements); each chunk keeps its path, its symbol or heading path and its line range, which is the citation. Only files whose (mtime, size) changed are read, and only those whose sha256 changed are re-chunked; deleted files leave the index. Hooks never write the index themselves: SessionStart adds one line (`Knowledge base: N files indexed (synced DATE); ...`) and, when a source changed since the last sync (a stat walk of at most 0.1 s that stops at the first newer file or folder, plus `.git/HEAD`, `.git/index` and `.gitignore`, each against its own source's last sync; a tree too big for that walk is re-synced when its index is a day old), starts a detached background `source-sync` (a lock keeps two apart, and a new one starts at most every five minutes, never while one runs; `LIVING_MEMORY_NO_BACKGROUND=1` turns it off). UserPromptSubmit adds up to two source excerpts (800 characters in all, usage kind `source`, each excerpt at most once a session) when notes gave fewer than two answers and the prompt's most informative words, chosen with the index's own vocabulary as for long prompts, are carried by a chunk (two words and two thirds of their weight; three words for a long prompt).

Live wiki connectors (`core/connectors.py`; the only network use besides `semantic install`; opt-in, explicit, credential by environment variable): `source-plan add` with `kind` `confluence` or `notion` registers a remote source with no folder. Payload: `name`, `domain`, `kind`, `token_env` (the NAME of an environment variable holding the credential, capital letters, digits and underscores; the token itself is never stored, and a payload that looks like a credential is refused), `base_url` (https; http only for 127.0.0.1 or localhost; no user, password or query; required for Confluence, default `https://api.notion.com` for Notion). Confluence: `space` (key), `root_page` (id: the page and its descendants) and/or `page_ids`; `api_path` defaults to `/wiki/rest/api` (Cloud), use `/rest/api` for Server or Data Center; `token_env` holds a bearer token (a Data Center personal access token) sent as `Authorization: Bearer`, or `email:api_token` (Atlassian Cloud), sent as HTTP Basic. Notion: `database_ids` (every page of the database) and/or `page_ids`; the variable holds the integration secret and the integration must be shared with those pages; sub-pages are not followed, list them or put them in a database. `source-sync NAME` (or `source-sync --all-remote` for every remote source of the domain) pulls the pages into the derived cache `<store>/sources-cache/NAME/` (Confluence `body.export_view` as `.html`; Notion blocks converted to Markdown: paragraphs, headings, lists, to-dos, code, quotes, callouts, toggles, tables, six levels of nesting) with a `manifest.json` {page_id: title, version or last_edited_time, url, path}, then indexes it like an HTML export or Markdown folder; hits cite the page title and URL (`citation` is `Title <url>`, `file` the URL). It is incremental (a page with an unchanged version is not rewritten, a Notion page with an unchanged `last_edited_time` is not fetched), follows removals (pages gone from a completed listing leave the cache and the index), and `source-sync NAME --rebuild` fetches every page again. Limits: 20 s per request, at most three retries on 429 and 5xx (Retry-After honoured, up to 30 s), 5,000 pages, 2 MB per page (larger ones are skipped and listed in the manifest), 5,000 blocks per Notion page, 600 s per sync; redirects to another host are refused; credentials found in a page are redacted before it is written to the cache. A failure (a wrong token, a timeout) exits 2 with a message that never carries the token, keeps the cache as it was, and is recorded in the manifest: `sources` shows each remote source's last sync, page count and last error, and `doctor` warns. Only the explicit command reaches the network: plain `source-sync` (the SessionStart background sync, `--rebuild` without a name) only re-indexes the cache it has, and the permission layer never auto-allows `source-sync NAME` for a remote source or `--all-remote` (the host prompts; subagents and viewers are refused). The cache is derived: not canonical, not backed up, not relocated; a removed source's cache goes at the next full `source-sync`. Deferred: SharePoint and Google Docs connectors.

Systems: a system is a `system/<slug>` tag plus an entry in `<store>/systems.json`: slug, name, status active|deprecated|retired, `description` (its purpose, 500 characters at most), `owners` (10 at most), `capabilities` (20 at most), absolute `repos` (10 at most; may be empty for a system you depend on but do not own), `depends_on` (slugs of other registered systems; `systems` derives `dependents` from it), `architecture` (the absolute folder holding its Architecture Suite output, or null) and a `passport` note ref. Systems exist only through `system-plan`, never `taxonomy-plan`. `system-plan create` payload: `{"slug":"billing","name":"Billing","description":"...","owners":["Payments team"],"capabilities":["Take payments"],"repos":["C:/path/repo"],"depends_on":["ledger"],"architecture":"C:/path/architecture/billing","passport":{"domain":"optional","title":"optional","body":"The summary ..."}}` makes one plan (kind `system_create`) that adds the tag, the registry entry and the passport note (a `context` note tagged `system/<slug>`; domain: `passport.domain`, else the domain bound to `repos[0]`, else global). `update` takes the slug and any of those fields plus `status` (kind `system_update`; `passport` is then a note ref) and `retire` takes `{slug}` (kind `system_retire`); both change only `systems.json`. `capture --system SLUG` adds `system/SLUG` to a new note. A system's passport is assembled by readers from the registry entry and its tagged notes: `runbook` notes are its runbooks, `decision` notes its architectural decisions, `risk` and `bug` notes its weaknesses and debt. Auto-attribution works as for projects (above), by the system's `repos`, for active systems only, and reports `system_candidates`; a note in a repo that belongs to both a project and a system gets both tags. `systems` and `doctor` warn about a missing repo or architecture folder, an unregistered system tag, an unknown `depends_on` slug or a passport ref that no longer resolves. `systems.json` is protected config and part of `backup`.
Changes: a change is a numbered unit of work, an entry in `<store>/changes.json` plus a brief (a `plan` note); it is not a plan's file changes. Fields: `id`, `title` (1-120 characters, no `[`, `]`, `|` or `#`, because notes link to the brief as `[[CHG-014 Title]]`), `project` (a registered project slug), `brief` (a `domain:id` note ref), `stage` explore|design|implement|validate (default explore), `status` active|done|cancelled (default active), `repo` (an absolute folder or null), `branch` (200 characters at most or null), `system` (a registered system slug or null), `element` (an architecture element, 120 characters at most or null; needs `system`), `created` and `updated`. The id is a store-wide integer shown as `CHG-014`; it is allocated at plan time and provisional until apply (a second plan made from the same registry gets the same number and goes stale). Changes exist only through `change-plan`; `changes` lists them with `display`, `brief_status` and the brief's open and done Action Item counts as `actions`, and warns about an unknown project or system or a brief that no longer resolves. `change-plan create` payload: `{"project":"slug","title":"...","brief":{"domain":"optional","title":"optional","body":"The summary ..."},"stage":"explore","repo":"C:/path/repo","branch":"feat/x","system":"billing","element":"Ledger"}` makes one plan (kind `change_create`) that adds the registry entry and the brief; `title`, `project` and `brief` are required. The brief is a `plan` note tagged `subject/project`, `concern/workflow`, `project/<slug>` and, with a system, `system/<slug>`, titled with the display id (`CHG-014 <brief.title, else title>`); its domain is `brief.domain`, else the domain bound to `repo`, else the one bound to the project's first repo, else global. `brief` may instead be the ref of an existing active `plan` note that is not already a brief, which is adopted: it keeps its title and gains the missing project and system tags. `update` takes `{"id":14}` (or `"CHG-014"`) plus at least one of `title`, `stage`, `status`, `repo`, `branch`, `system`, `element` (kind `change_update`), and `close` takes `{"id":14,"status":"done"}` with status done (default) or cancelled (kind `change_close`); both change `changes.json`, and closing resolves the brief and setting an update's status back to active reopens it, in the same plan. There is no `change/` tag facet: tie a note to a change by linking to its brief (`--link '[[CHG-014 Title]]'`). Undoing a create frees the number; `cancelled` is the way to abandon a change; correct a mistake with a new `update`. Known limits: `update` never retags the brief (changing `system` leaves the old `system/` tag on the note); a change whose brief was deleted can still be updated and closed but shows a warning. `changes.json` is protected config and part of `backup`.

Cross-domain reads: `open` and `review` take `--all-domains` (every domain folder; the result's `domain` is null) and `--tag` (repeatable, all must match). `review` rows also carry `revision` and `domain`, so a client can snooze with `update --expected-revision` without another read.

Metadata-only updates keep `updated`: an `update` or `retag` that changes only `tags`, `review_by` and/or `files` leaves `updated` alone. `updated` means the content changed and drives recency and review age, so triage, retagging and snoozing must not reorder recency lists or reset the review clock. Changing the title, body, type or context still bumps it.

Capture types: knowledge, decision, preference, context, status, bug, plan, risk, research, policy. [Note types and use cases](NOTE_TYPES.md) defines each type, examples and the boundaries between related types. STATUS includes progress and milestones; corrections use KNOWLEDGE with `concern/correction`. Type determines the uppercase filename prefix: `decision` produces `DECISION - ...`, `bug` produces `BUG - ...`. Canonical schema-3 frontmatter stores type and omits prefix; read/search responses derive it. `--prefix` is a compatibility assertion that must match the type; omit it for new captures. The default type is knowledge. Bug resolve/reopen changes status and moves between archive/notes, retaining type bug and prefix BUG.

Use `note-type-plan` to preview conversion of existing notes, then `inspect-plan ID` and `apply ID --expected-plan-sha256 HASH` to review/apply it. Legacy BUG/RESOLVED prefixes become type bug; progress becomes status and correction becomes knowledge. Other notes retain their type. IDs, created timestamps, tags, lifecycle statuses and history are preserved. The plan updates local Markdown links for renamed files. Legacy notes remain readable until converted. To change an individual type, use `plan update REF` with payload `{"type":"bug"}`; its approved apply renames the file and updates local links. Resolved bugs must be reopened before changing to a non-bug type.

Facet flags accept `--subject x` or `--subject subject/x`. When a capture names no `subject/` tag it gets `subject/user` for preferences and `subject/project` otherwise. When it names no `concern/` tag, decision, preference, bug, knowledge and policy notes get `concern/decision`, `concern/preference`, `concern/bug`, `concern/knowledge` and `concern/workflow`. A default is used only if the tag is in the taxonomy, and the result reports it as `inferred_tags`. With `--session` and no `--domain`, capture, update and capture-finalize use the domain the hooks pinned for that session. Credentials are rejected by default. `--redact` on capture or update replaces each one with `<redacted type='KIND'/>` (an assignment keeps its key name) and reports `redacted: [{kind, field}]`.

Open work: `open` lists the unchecked action items of active plan, bug and risk notes in the active and parent domains, newest note first. Each item has `ref`, `short_ref`, `title`, `index` (1-based among the note's items) and `item`. `check REF ITEM` ticks one item, matched by exact text (case-insensitive), else by a unique part of it; `--index N` picks one by position, and `--undo` unticks. It changes only that checkbox, as a journaled update: `undo` reverts it, and with `--session` it records the turn's receipt. Ambiguous text fails with `ambiguous_item` and lists the candidates. Both commands are auto-allowed. `open` is read-only, so subagents may run it. When `check` ticks the last open item it returns a `hint` naming `resolve REF`. `resolve REF` marks a plan, bug or risk note resolved and moves it to the archive, so finished work leaves session context and search; it is a journaled, undoable change that needs no plan, and `reopen REF` reverses it. SessionStart names active notes whose action items are all done.

Provenance: the PreToolUse hook records the paths, never the content, of files the main agent changes in a turn. Paths are relative to the bound project folder, or absolute outside it; scratchpad and memory-store paths are skipped, and shell commands count only for files inside the project. Captures and updates with `--session` list the turn's paths not yet on the note as `suggested_files`. `--files auto` stores them in the note's `files` property, `--file PATH` adds one, and on update `--files none` clears the list (update otherwise adds to it). Captures with `--session` also store `origin: "HARNESS:SESSIONHASH"`, a 12-character hash rather than the session ID. `files` is editable in Obsidian; `origin` is not. `search --file PATH` with no query lists notes whose `files` include the path, or anything under it if it is a folder, followed by notes that name the path in their body. It honors `--scope`, including the foreign fallback; `--filter` needs a query. With a query, `--file` acts as a filter.

Usefulness: `stats` summarises the local usage diary (see [MAINTENANCE.md](MAINTENANCE.md)) for the active and parent domains. It returns `noisy` (retrieved for a prompt or a file 3+ times and never read, updated, checked, superseded, confirmed, resolved or re-captured; session-start guidance and codebase maps are standing context and are counted apart as `standing`), `used` (most used first), `reminders` by kind (`nudge-preference`, `nudge-correction`, `nudge-decision` and `nudge-remember` for the line a prompt adds to its own context; `remember`, `explored` and `grown` for a Stop continuation) and `signal_captures` per ISO week. Each note entry has `ref`, `short_ref`, `title`, `status` (`missing` once a note is gone) and its non-zero `counts`. It is read-only and auto-allowed, and subagents may run it.

Operational log: `logs` returns `level_setting`, `matched` and `entries`, newest first, from the local operational log (see [MAINTENANCE.md](MAINTENANCE.md)): hook runs, command runs and absorbed exceptions, metadata only. `--level` is the lowest level shown (default info). `--days` is at most 30 and `--limit` at most 1000. The command does not log itself. `LIVING_MEMORY_LOG_LEVEL` (`debug|info|warning|error|off`, default info) sets what is written. `debug` adds each hook's decision detail and each command's result status. `LIVING_MEMORY_LOG_CONTENT=1` adds text, but only for a sandbox store (see MAINTENANCE.md). It is read-only and auto-allowed, and subagents may run it.

Timeline: `timeline` lists the active domain's notes in date order around an anchor, answering "what else was decided around then?". The anchor is a REF, else the first note on or after `--date`, else the newest note. It shows `--before`/`--after` notes either side (default 5, at most 50) by `--by updated` (the default) or `created`. `--type` (repeatable) narrows the list but always keeps the anchor. `--all` includes superseded, archived and resolved notes; a retired anchor is always shown. Each row has `ref`, `short_ref`, `date`, `type`, `title` and `status`, and the anchor row has `anchor: true`. It is read-only and auto-allowed, and subagents may run it.

Auto-memory ingest: `ingest-plan` turns Claude Code auto-memory topic files into notes in the active domain, as a reviewed plan (`inspect-plan`, then `apply`). The default source is Claude's folder for `--cwd`: `CLAUDE_HOME/projects/<cwd with every non-alphanumeric character as ->/memory`. `MEMORY.md`, symbolic links, files over 64 KB and non-UTF-8 files are skipped. The frontmatter `metadata.type` (or `type`) maps user and feedback to preference, project to context, and reference to knowledge. `name` becomes the title, `description` the summary, and the body's lines become Details bullets (headings become bold labels). Tags default from the type; context notes get `concern/knowledge`. Each note's capture key is `auto-memory:` plus the file's SHA-256, and its ID derives from that key. A re-run, or a second plan for the same files, therefore adds nothing once one plan is applied: unchanged files are listed under `unchanged`, and a stale duplicate plan fails to apply. Files with credentials are skipped unless `--redact` is given; near-duplicate titles are skipped unless `--allow-similar` is given. The result lists `created`, `unchanged` and `skipped` with reasons. It is not auto-allowed, and subagents may not run it.

Bundles: `export --out FILE` writes a zip of the active domain's notes: active notes only, or every note with `--all`. `--type` (repeatable) keeps any of the types, and `--tag` (repeatable) keeps notes carrying all the given tags. The zip holds the canonical files as they are, under `notes/` and `archive/`, plus `manifest.json` (`schema`, `domain`, `exported`, each note's `id`, `path` and `sha256`, and the tags used). It refuses an existing file or a path inside the store's domains. `import-plan FILE` checks that every member is listed in the manifest with a matching hash and lies inside the bundle layout. It then proposes a plan that adds the bundle's notes, keeping their IDs, to the bundle's domain, or to the domain `--domain` names, which must be bound. A note already present unchanged is listed as `unchanged`. One present with other content is a `conflict` and is not written, so update it instead. Retired notes go to `archive/`. Tags outside this store's taxonomy reject the import, and the message names the `taxonomy-plan` command to run first. Re-importing a bundle proposes nothing. Neither command is auto-allowed, and subagents may run neither.

Title/body duplicate detection and optional idempotency keys prevent accidental repeated capture. A duplicate requested with a different type is rejected; update that note instead. Capture arrays and generic `batch` each accept at most 20 items. Batches serialize individual operations and return individual receipts; they are not an all-or-nothing multi-capture transaction. Generic batch payload: `[{"argv":["search","cache"]},{"argv":["taxonomy"]}]`.

Apps: these commands serve a desktop app or other human-facing tool.
- `serve --stdio` keeps one process open and reads one JSON request per line on stdin: `{"id":ANY,"argv":["COMMAND",...],"stdin":"optional text"}`. The command comes first and its options follow it. `--root` and `--cwd` default to the server's. `stdin` stands in for standard input, for commands that read a payload from it.
- Each request gets one reply line: `{"id","exit_code","result","error"}`. `result` is the command's usual JSON. `error` is `{code,message}`, or null when `exit_code` is 0. Exit codes match the CLI. A malformed request gets `exit_code` 2 and does not end the server; end of input does.
- Requests run one at a time, in-process, as `batch` runs them, so there is no Python start-up per call. `serve` and `setup` are not accepted as requests. Only the main actor may start the server. Each request may pass `--actor viewer` or `--actor main`.
- A loaded semantic model stays mapped for the server's lifetime. On Windows, stop the server before another process runs `semantic remove`.
- `list` returns one page of notes for `--domain`, or for every domain folder with `--all-domains`, newest update first. Options: `--status active|resolved|archived|superseded|any` (default active), `--type` (repeatable), `--tag` (repeatable, all must match), `--with-summary`, `--offset`, and `--limit` (default 200, at most 1000).
- Each `list` row has `ref`, `id`, `domain`, `title`, `type`, `status`, `tags`, `created`, `updated`, `revision` (pass it to `update --expected-revision`) and `path`, relative to the store. With `--with-summary` each row also has `summary` (the summary as plain text, at most 300 characters), `files` (the note's files list, or `[]`) and, for plan, bug and risk notes only, `actions: {open, done}` (checkbox counts in Action items).
- `domains` lists bound domains and any domain folder on disk. Each has `bound`, `prefixes`, `active` and `archived` note counts. The result also includes `aliases`, `global_domains` and `foreign_domains`.
- `version` returns `api` (bumped when the app surface changes incompatibly; 2 adds `open`/`review` `--all-domains` and `--tag`, `list --with-summary`, `review` rows with `revision` and `domain`, and project auto-attribution), `python` and `commands`.
- `links` returns the link graph of `--domain`, or of every domain folder with `--all-domains`. By default it covers active notes only; `--status any` adds archived, resolved and superseded notes.
  - A `[[Title]]` link resolves the way a title REF does: case-insensitive, first in the linking note's domain, then its parent domains, then the global domains. Text after `|` or `#` is ignored. An active note wins a title over a retired one.
  - The result has `nodes` (`ref`, `id`, `domain`, `title`, `type`, `status`, `tags`; it includes linked notes from parent or global domains) and `edges` (`from`, `to`, `kind` `link` or `supersedes`, newer note to the note it replaced). It also has `unresolved` (`from`, `target`) for links that match no note.
  - A note has at most one edge to another note, and a link wins over supersedes. Self-links are skipped.
- `--actor viewer` is read-only. It allows every subagent command plus `taxonomy`, `review`, `diff` and `inspect-plan`. Its `read` writes no usage-diary event, so browsing does not change `stats` or note strength.
- `list`, `domains`, `version` and `links` are read-only, and subagents may run them.

Search defaults to active, parent and configured global domains, then explicitly configured foreign domains only after zero scoped hits. `--scope all` is explicit and includes the global domains. As for prompts, relevance is judged within each domain before the merge, and global notes rank like the active domain's; `relevant` is false when nothing passed that check, and the closest matches are returned with a `hint`. Filters use `--filter tag=concern/decision`, prefix/status/type. Stale unfiltered retrieval falls back to canonical BM25; stale filtered retrieval requires `--rebuild`. `score` ranks results; `relevance` is the share of informative query terms found in the note's title or body. With a semantic model installed, `engine` is `fts5+semantic` and each hit has `similarity`: the cosine between the query and the note's best unit (its title plus summary, its caveat, or one section; see the unit index below), or between the query and its title plus summary when the unit index is missing or stale. Every hit has `backend` (`native`, `python`, `notes` or `lexical`) and, when the first choice was not available, `backendReason`; `evidence` lists up to two matched sections as `{heading, role, lines, similarity}` (lines are file lines; `read REF --section HEADING` returns that section's text, as `{section:{heading, role, lines}, body}`). `--explain` adds `explain:{model, native, native_enabled, semantic:{domain: {backend, reason, vectors, semantic_candidates, lexical_candidates, ms}}, candidates:[{ref, rank, engine, engine_score, relevance, similarity, gate}], prompt_hook:{ref: {level, section}}}`: why each note was found, the gate's verdict, and what the prompt hook would deliver for this text (no note text).

Semantic search: `semantic install` downloads the pinned model (potion-retrieval-32M, about 130 MB) into `<store>/.models/` from Hugging Face. The first load of a model writes `tokenizer.marshal` beside tokenizer.json (a parsed-tokenizer cache, derived, safe to delete). `--from DIR` copies the files from a folder instead, for an offline install. Every file's SHA-256 must match the pinned value, and nothing replaces the old model until all of them do. It then rebuilds every domain's index with a vector per note. Search fuses the lexical and semantic rankings with reciprocal rank fusion (k = 60). A prompt injects a note found by meaning alone only when its similarity reaches the model's `min_similarity` (0.45), and one-word prompts still need a title match. `semantic remove` deletes the model and rebuilds the indexes lexical-only. `semantic status` reports `enabled`, `model`, `dim` (read from the model file), `size_bytes`, each index as `vectors` or `lexical`, `backend` (what a prompt would use now: `native`, `python` or `lexical`), `native:{installed, loadable, version or reason, enabled}`, `units:{domain: {units, notes, vectors, generation, mode, native_table fresh|stale|absent, size_bytes, updated}}`, and `error` when the model cannot be read; search then stays lexical, and `doctor` warns. The model is read with the standard library: no pip package, and no network after install. Section-level units (`domains/D/vectors.sqlite3`) are kept by every index rebuild; `semantic rebuild` discards and rebuilds them for every domain. Native vector search is optional: `pip install sqlite-vec==0.1.9` (any 0.1.x from 0.1.6) into the Python the hooks run, then `semantic rebuild`; nothing is downloaded by Living Memory itself, and without the package everything works with the same results in Python. `semantic native off` (stored in `<store>/.models/native.json`; `LIVING_MEMORY_NATIVE=0` for one process) keeps the extension unloaded; `semantic native on` allows it again; `semantic native` alone reports. None of these is auto-allowed. Neither install nor remove is auto-allowed, and subagents may run none of the three. SQL is read-only, one statement, at most 100 rows, five-second execution budget.

Mutation plans snapshot all touched files and require their exact digest. `undo` creates a new plan and rejects later conflicting edits. `inspect-plan` bounds each diff at 16,000 characters and marks truncation. Overlay teardown plans are rooted at the vault: inspect/apply them with `--root VAULT`. Package plans are rooted at the install folder (the parent of `app/`), adapter plans at each harness home, and the legacy-copy retirement plan at CODEX_HOME.

With `--session`, capture and update refuse text that repeats a `<private>` span from the session's prompts, with a `private_content` conflict (see PROTOCOL.md).

Error exit codes: invalid=2, conflict=5, stale=6. The code comes from the message's own wording, the text before any quoted value or `: detail`. A note title, tag or path quoted in a message never changes it. Native host event wrappers fail with their adapter's bounded output contract.

`scripts/safe_write.py DOMAIN notes/FILENAME --content-file FILE --expected-revision HASH` returns an approved update plan, not a direct write.
